## Data Flow Diagrams

### Primary Document Lifecycle: Partner → Demand → Deal → Offer → Proforma → Invoice → Journal

```
  +---------+        +---------+        +--------+        +--------+        +---------+        +---------+        +---------+
  | Partner | -----> | Demand  | -----> | Deal   | -----> | Offer  | -----> | Proforma| -----> | Invoice | -----> | Journal |
  | (create)|        | (draft) |        | (open) |        |(OF-NNN)|        |(PRO-NNN)|        |(INV-NNN)|        |  (auto) |
  +---------+        +---------+        +--------+        +--------+        +---------+        +---------+        +---------+
       |                                                                       ^                    ^                ^
       |                                                                       |                    |                |
       +--- portal/login -- portal/kyc/submit -- kyc/approve -- auto-create ---+                    |                |
                                                                                                         |                |
                                                                       automation/create-invoice-from-proforma + invoices/record-payment
```

Step-by-step:

1. **`POST /api/portal/login`** — partner authenticates via portal session
2. **`POST /api/portal/kyc/submit`** — partner submits KYC documents (writes `kyc_submissions` + `portal_uploads`)
3. **`POST /api/kyc/[id]/approve`** — admin approves; **`store.approveKycAndTransfer()`** auto-creates a `partners` row + links `portal_access`
4. **`POST /api/automation/create-demand-from-portal-rfq`** — partner RFQ (in `portal_rfqs`) becomes a `demands` row
5. **`POST /api/automation/create-offer-from-deal`** — a deal becomes an offer, auto-numbered `OF-<year>-<NNN>`
6. **`POST /api/offers/[id]/send`** — offer transitions to `sent`, partner is notified via portal
7. **`POST /api/portal/offers/[id]/respond`** — partner accepts/rejects; on accept, an optional auto-proforma is created
8. **`POST /api/automation/create-proforma-from-offer`** — copies offer data into a proforma `PRO-<year>-<NNN>`
9. **`POST /api/proformas/[id]/send`** — proforma sent, partner notified
10. **`POST /api/automation/create-invoice-from-proforma`** — proforma becomes invoice `INV-<year>-<NNN>`
11. **`POST /api/invoices/[id]/send`** — invoice issued
12. **`POST /api/invoices/[id]/record-payment`** — invoice → `paid`; **`store.autoJournalFromInvoice()`** auto-creates an `erp_journal_entries` + `erp_journal_lines` row
13. **`POST /api/erp/journal-entries/[id]/post`** — manual post (or auto-posted)
14. **`GET /api/erp/reports`** — trial balance / P&L reflects the posted entries

### ERP Auto-Journaling

Three store methods auto-create double-entry journals from business events:

| Trigger | Store method | Writes |
|---|---|---|
| Invoice marked paid | `store.autoJournalFromInvoice(invoiceId, tenantId, userId)` | `erp_journal_entries`, `erp_journal_lines` |
| Deal closed | `store.autoJournalFromDeal(dealId, tenantId, userId)` | `erp_journal_entries`, `erp_journal_lines` |
| Commission marked paid | `store.autoJournalFromCommission(commissionId, tenantId, userId)` | `erp_journal_entries`, `erp_journal_lines` |

### QR Document Verification Flow

1. **`POST /api/document-register`** (or any document create) — generates a `verification_code` in `document_verifications`
2. **`GET /api/verify/[code]`** — public endpoint, returns verification metadata, logs to `verification_logs`
3. **`POST /api/document-verify/by-doc`** — staff-side lookup by document type + ID
4. **`POST /api/document-verify/forensic`** — advanced forensic check (file hash comparison)

### Architectural Observations

1. **Two parallel auth flows.** Staff use session cookies (`requireAuth`/`requireAdmin`/`requireSuperAdmin`); partners use portal sessions (`getPortalSession` from `@/lib/auth/portal-session.ts`); API keys authenticate via `requireAuthOrApiKey` (hybrid). Most read/list endpoints accept both staff-session and API-key.

2. **Store abstraction decouples routes from DB.** No route touches Supabase/Prisma directly — all DB access goes through `auth.store.X()` or `getStore().X()`. The concrete implementation is chosen at boot via `DB_BACKEND` env var (`supabase` | `prisma` | `mock`). Trade-off: the `tables` column in this audit is *derived* by inspecting which store methods a route calls and resolving them through the `supabase-store.ts` implementation.

3. **Inconsistent permission gating.** Many routes wrap permission checks in dynamic `import("@/lib/permissions/can")` followed by `requirePermission(auth, "X.read")` inside an IIFE. The API-key branch does a separate `hasPermission(auth.permissions, "X:read")` check (using `:` separator, while `requirePermission` uses `.`). Consolidating into a single helper would eliminate duplication and the separator mismatch.

4. **Tenant isolation is post-filtered.** List routes like `GET /api/offers` call `store.listOffers(tenantId)` and then **post-filter** by `tenant_id` for non-super-admin and API-key callers, because `PrismaStore.listOffers` ignores `_tenantId`. With Supabase RLS this is belt-and-braces, but the dual-path is fragile if a new store backend is added.

5. **Document numbering has a race retry.** All create routes (offers/proformas/invoices) auto-generate document numbers via `store.listX({limit:1}).total + 1`, with a unique-collision retry that bumps the sequence by 1. A dedicated `document_sequences` table exists in the schema but is not yet wired into all routes — this would be a more robust solution.

6. **Automation routes bypass API-key auth.** All `/api/automation/*` routes use `requireAuth()` (session-only). If third-party automation via API key is desired, this needs to be widened to `requireAuthOrApiKey()`.

7. **Quota enforcement is consistent.** All document-create routes call `enforceQuota(tenantId, "monthly_documents", isSuperAdmin)` from `@/lib/api/plan-limits`. Good pattern.

8. **Module feature flags.** 87 routes are gated by 13 module flags (`module_finance`, `module_trade`, `module_portal`, `module_logistics`, `module_kyc`, `module_document_templates`, `module_document_verification`, `module_vault`, `module_api_keys`, `module_webhooks`, `module_mail_queue`, `module_security`, `module_inventory`). The `module_crm` flag is defined but no routes use it yet — CRM module is not implemented.

9. **Two password-reset flows.** `POST /api/portal/forgot-password` + `POST /api/portal/reset-password` use hashed tokens stored in the `password_resets` table (via `src/lib/auth/password-reset.ts`). Staff users have no equivalent flow — only `POST /api/users` (admin-only) to reset another user's password.

10. **No `/api/auth/me` permission check.** `GET /api/auth/me` returns the full user object (including role and tenant_id) without requiring any permission. This is intentional (used on page load) but worth noting in a security review.

## Tools & Methodology

- **Route extraction**: `rg -oP 'export async function (GET|POST|PUT|DELETE|PATCH)'` across all 210 `src/app/api/**/route.ts` files.
- **Store-method-to-table mapping**: parsed `src/lib/data/supabase-store.ts` with a regex-based parser to associate each `async methodName()` with the `.from("<table>")` calls in its body. This produced a 210-method lookup table.
- **Route-to-table resolution**: each route's `auth.store.X()` / `store.X()` calls were resolved through the lookup table to produce the final `tables` column.
- **Component-to-route mapping**: scanned `src/components/**/*.{ts,tsx}` for `api(...)` and `fetch("/api/...")` patterns, normalizing dynamic segments (`/${id}` → `/[id]`) and stripping template-literal interpolations.
- **Auth classification**: routes that import `getPortalSession` from `@/lib/auth/portal-session` are tagged `PortalSession`; otherwise the `requireAuth/Admin/SuperAdmin/ApiKeyAuth` pattern is detected.
- **Cross-category coupling**: a route is flagged as cross-domain if its resolved tables span 2+ business categories (e.g., an `Automation` route touching both `offers` and `proformas`).
