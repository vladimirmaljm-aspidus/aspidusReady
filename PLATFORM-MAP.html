Architecture Stack

Next.js 16 App Router → API route handlers → requireAuth/Admin/SuperAdmin/PortalSession (helpers.ts) → auth.store.X() abstraction (store.ts) → SupabaseStore (default) / PrismaStore / MockStore → PostgreSQL (Supabase) with RLS (row-level security) on tenant_id.

Multi-tenant Isolation

Every business table has a tenant_id column. Routes resolve tenant via resolveTenantId(auth, req) and either pass it explicitly to store.listX(tenantId, ...) or rely on RLS policies to filter automatically. Super-admin users bypass tenant filtering (with optional ?tenant_id= override). API Keys are scoped to a single tenant.

Business Data Flow

Architectural Observations

  • Two parallel auth flows. The platform supports both session-cookie auth (requireAuth) for staff UIs and JWT/cookie portal sessions (getPortalSession) for partner portals, with API-key auth (requireAuthOrApiKey) as a third option. Most read/list routes use requireAuthOrApiKey to allow both.
  • Store abstraction decouples routes from DB. No route touches Supabase/Prisma directly — all DB access goes through auth.store.X(). This means DB migrations (Supabase ↔ Prisma) only require changing the store implementation. Trade-off: the tables column in this report is derived by inspecting which store methods are called and resolving them via the supabase-store implementation.
  • Inconsistent permission gating. Some routes use inline dynamic requirePermission(auth, "X") wrapped in import() calls; the API key path does a separate hasPermission() check. Consolidation into a single helper would reduce duplication.
  • Tenant isolation is post-filtered. Several list routes (e.g. GET /api/offers) call store.listOffers(tenantId) and then post-filter by tenant_id because PrismaStore ignores tenant scoping. With Supabase RLS this is belt-and-braces, but the dual path is fragile.
  • Document numbering sequences. Document numbers (OF-/PRO-/INV-/YYYY-NNN) are computed at runtime via store.listX(limit:1).total + 1 — there is a race-condition retry loop, but a dedicated document_sequences table exists in the schema and is not yet wired into all routes.
  • Automation routes bypass some gates. The /api/automation/* routes call requireAuth (not requireAuthOrApiKey), meaning they cannot be triggered via API keys. If third-party automation is desired, this needs to be widened.
  • Quota enforcement. All create routes for documents (offers, proformas, invoices) call enforceQuota(tenantId, "monthly_documents", isSuperAdmin) to enforce plan limits. This is consistent across the board.
  • Module flags. 87 routes are gated by 13 module flags (module_finance, module_trade, etc.) enabling plan-based feature toggling. The module_crm flag is defined but no routes use it yet (CRM module not implemented).
